# E3: состояние расчёта полного парка

## Что уже можно использовать

- `SourceSnapshotE3Adapter` читает сохранённый D1 snapshot `FULL43`: 43 состава, 1428 закреплённых рейсов, восемь циклов, пять альтернативных путей ТО, окна присутствия, 340 уборок, пять временно недоступных составов, пять закреплённых работ и четыре резервных состава. Исходный hash проверяется до построения модели.
- CP-SAT выбирает один из разрешённых путей для каждой работы; независимая интервальная проверка проверяет фактически выбранный путь.
- `GET /api/v1/source-snapshots/{id}/e3-assessment` сообщает hash, размеры модели и работы, для которых при **текущем закреплении рейсов** нет непрерывного окна. Отсутствие таких блокеров было бы только необходимым условием допустимости, не доказательством готового плана. `d2Status` поэтому всегда `NOT_PERFORMED`.
- Assessment показывает подтверждённую ёмкость: в модельном FULL43 статус `AVAILABLE` имеют 34 состава, а одновременно выполняются 34 рейса; составов со статусом допуска и без исходных рейсов нет. Пять составов в депо имеют статус `MAINTENANCE`, и время окончания исходной занятости само по себе не является выпуском на линию.
- `E3TripAssignmentLedger` хранит предложенное назначение отдельно от неизменных исходных рейсов, проверяет маршрут, подготовку, занятость и границу заморозки и пересчитывает пробег по фактически назначенным рейсам. `E3TripAssignmentAudit` независимо восстанавливает эти же факты из D1 snapshot. Это внутренний проверяемый контракт для будущего solver, пока не готовый план ТО.
- `E3MileageObligationRecalculator` заново выводит пробеговые рубежи и обязательные работы из предложенного назначения рейсов. `E3MileageObligationAudit` отдельно читает сохранённый D1 snapshot и проверяет рубежи, допуски, старший цикл, сроки и параметры каждой работы, не вызывая генератор. Обе проверки относятся к промежуточной проекции: они не подтверждают размещение ТО, уборку и выпуск.
- Подтверждённый модельный резервный состав можно предложить вместо линейного. `E3TripAssignmentAudit` отдельно требует доказательства его присутствия и резерва в исходном городе до первого отправления; `E3ReserveCoverageAssessment` считает оставшийся резерв по каждому городу и явный дефицит. Дефицит виден, но не превращается в ложный D2 PASS. `E3CleaningCoverageAssessment` пересчитывает правило «после четвёртого рейса до пятого» по новому носителю оборота: старые закреплённые уборки исходного состава не покрывают заменивший его состав. Отсутствующие уборки ещё нужно разместить solver-ом.
- После интеграции заявок задача 1 передаёт в snapshot `urgentWorkRequirements` и `resourceOutages`. Срочную работу E3 явно отклоняет до появления подтверждённых длительности, ресурса и правил выпуска: она не может исчезнуть из плана молча. Для отключения ресурса E3 сверяет интервал с уже сокращёнными окнами доступности; независимый аудит выявляет оставшуюся доступность во время отключения. Узкий E2-адаптер отклоняет оба новых вида фактов.
- `E3SourcePlanAudit` независимо перечитывает сохранённый payload и сравнивает проекцию составов, ресурсов, рейсов, занятости, закреплённых работ, резерва и окон. Он не выдаёт PASS: правила пробега и эксплуатации пока не проверены полностью.

## Почему FULL43 пока нельзя рассчитывать и утверждать как полный E3

В модельном источнике каждому из 34 линейных составов уже назначены три рейса ежедневно в течение 14 суток. У части составов возникает длительное IS510–IS540. Между этими закреплёнными рейсами непрерывного окна нужной длительности нет. Это подтверждает `E3_NO_CONTIGUOUS_SERVICE_WINDOW` на сохранённом snapshot. Простое добавление уборок или дополнительных путей депо не устраняет конфликт: на время длительного ТО рейсы должен взять другой пригодный состав. Модельный резерв может временно покрыть оборот с показом дефицита 2+2, но это меняет его собственные обязанности ТО и уборки; неподтверждённый выпуск пяти составов из депо нельзя подменить окончанием исходной занятости.

Замена состава меняет его последующие рейсы, город и пробег. Следовательно, нельзя оставить обязательства ТО, рассчитанные по старому списку рейсов, и назвать результат оптимальным. Нужно оптимизировать назначение рейсов и ТО согласованно, затем независимо проверить итоговый пробег каждого состава. Для использования пяти деповских составов нужен явный источник их выпуска после ТО; алгоритм не вправе считать их свободными только потому, что закончился интервал `UNAVAILABLE`. Пока этого нет, `FULL43.planningSupported=false`, запуск полного плана блокируется, а утверждение требует `D2=PASS` и допустимый статус solver.

## Следующий шаг реализации

1. **Назначение рейсов.** Использовать отдельные идентичности рейса и предложенного состава из `E3TripAssignmentLedger`; менять назначение можно только после текущего подтверждённого момента. Solver должен найти назначения, которые прошли независимую сверку, и учитывать явные факты выпуска состава. Текущий аудит сохраняет все рейсы и выявляет расход исходного резерва по городам; следующий шаг — проверить парность и допустимость дефицита на всём горизонте. Рейс не может исчезнуть или исполниться дважды.
2. **Совместный расчёт назначений и ТО.** Для каждого кандидатного назначения рубежи и обязательные работы уже можно пересчитать и независимо сверить. Следующий solver должен искать назначения совместно с интервалами ТО: длительные работы, уборка и выпуск занимают конкретные интервалы состава и ресурса. Уже начатые или согласованные работы остаются закреплёнными. Текущий пересчёт сам по себе не размещает работы.
3. **Полный независимый D2.** Диагностика уборок уже показывает работы, которые надо перенести на новый состав; требуется их размещение с длительностью и ресурсом, проверка парных рейсов, всех ресурсных ограничений, выпуска и закреплённых работ. Дефицит резерва по городам следует показывать отдельно от жёстких нарушений. Только проверенный результат solver может получить `PASS` и право на утверждение.
4. **Проверка на событии.** Заявка диспетчера создаёт новую версию исходных данных и новый snapshot. Планировщик запускает расчёт по новому hash; интерфейс показывает изменения назначений и ТО, отдельные статусы solver и D2. Старый согласованный план сохраняется для сравнения.

## Для параллельных задач

- **Задача 1, события и БД:** версии заявок и snapshot теперь сохраняются. Для полноценного FULL43 требуется отдельный подтверждённый факт выпуска пяти составов из депо после ТО; статус `MAINTENANCE` и окончание `UNAVAILABLE` недостаточны. Для `urgentWorkRequirements` нужны подтверждённые длительность, ресурс, допуск к движению после работы и источник этих нормативов. Передать в E3 норматив подготовки/выпуска и его версию.
- **Задача 3, интерфейс:** выводить `FULL43` как модельные данные и показывать результат assessment рядом со snapshot hash. Не предлагать утверждение, когда `d2Status` не `PASS`. Календарь полной 14-дневной перепланировки пока отсутствует; доступный оперативный пример первых суток не выдавать за него.

Интеграционный тест `CaseFleetIntegrationTest` проверяет чтение FULL43, endpoint и обнаружение искажённой проекции. Запускать его на Java 21 с тестовой PostgreSQL (`D1_TEST_DB_URL`); на локальной Windows Java 24 загрузка нативной библиотеки OR-Tools может аварийно завершить процесс, поэтому CP-SAT тесты запускаются в Linux/JDK21.
