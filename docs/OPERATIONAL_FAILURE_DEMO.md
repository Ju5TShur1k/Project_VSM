# Отказ перед рейсом: демонстрация и передача команде

Комментарий эксперта: в основном примере должны быть отказ перед отправлением,
предложение замены и явный дефицит резерва. Резерв допускается вывести на линию;
отремонтированный состав занимает его место после приёмки.

## Что реализовано

По умолчанию на экране «Парк» выбран FULL43. Источник содержит 43 состава,
34 на линии, 5 в плановом ТО, четыре в резерве (два в каждом городе),
1428 модельных рейсов на 14 суток. Оперативная сессия работает с первыми сутками:
102 индивидуальных рейса, 51 парная отправка. Идентификатор пары объединяет
два состава одного отправления; это не 102 отдельных парных отправления.

Оператор регистрирует блокирующий отказ перед ближайшим рейсом. Состав снимается
со всех оставшихся рейсов его текущего суточного оборота. Система проверяет
кандидатов, оператор согласует замену, сервер повторно проверяет решение.
Времена, маршруты и второй состав каждой пары сохраняются.

Проверяются: свободный резерв, город отправления, подтверждённое модельное окно
присутствия либо отдельная приёмка отремонтированного состава, подготовка,
ТО/уборка/закреплённая работа, пересечения рейсов, непрерывность маршрута,
счётчик уборки и пробеговые ограничения всего оставшегося суточного оборота.
Само назначение в резерв не означает запрет его использования.
Причины отказа в кандидатуре видны пользователю.

Неизвестный счётчик уборки блокирует кандидатуру. После четвёртого рейса нельзя
предложить пятый без принятой уборки. Запланированное окно CLEANING не считается
фактом выполнения. Пробег проверяется по активной абсолютной сетке и допуску
от номинальной отметки; другая или неподтверждённая трактовка правил отвергается.

Цель 2+2 применяется как отображаемый дефицит, а не жёсткий запрет замены при
расходовании резерва. Если допустимого состава нет, рейсы остаются непокрытыми,
система показывает нарушенные парные отправки. Резерв из другого города не
перемещается мгновенно и не предлагается без достаточных условий.

Прогноз ремонта не возвращает состав в резерв. Оператор отдельно фиксирует
время завершения ремонта, приёмку, город и документ. Место должно совпадать
с положением состава. После приёмки исходный поезд становится резервным,
замещающий продолжает оборот. Снятые рейсы не возвращаются автоматически.

## Порядок показа: 1–2 минуты

1. Войти, выбрать «43 состава · отказ перед рейсом, замена и резерв»,
   нажать «Загрузить выбранный набор». Каждое нажатие создаёт новую независимую
   оперативную сессию. Первоначально: Москва 2/2, Санкт-Петербург 2/2,
   непокрытых рейсов 0.
2. Выбрать CASE-01, отправление 01.07.2031 06:00 Санкт-Петербург → Москва,
   MODEL-PAIR-1-D1-R1. Отказ — 05:00, прогноз ремонта — 09:00.
   Зарегистрировать отказ. Становится 3 непокрытых рейса и 3 неполных пары.
3. Согласовать CASE-42. Все три оставшихся рейса дня назначены замене,
   непокрытых рейсов 0, резерв Санкт-Петербурга 1/2. Время и второй состав пары
   неизменны. Показать причины отказа московским кандидатам.
4. Для демонстрации обмена резервом: раскрыть «Проверить, что прогноз ремонта…»,
   продвинуть модельное время до 10:00. Резерв остаётся 1/2.
   Затем открыть приёмку CASE-01: завершение ремонта 09:30, приёмка 10:00,
   заполнить модельный документ, подтвердить. Резерв Санкт-Петербурга — 2/2.

Альтернативный стрессовый показ из новой сессии: последовательно зарегистрировать
в 05:00 отказы CASE-01 → замена CASE-42 и CASE-05 → замена CASE-43;
затем CASE-09 без замены. Во всех трёх случаях выбирать рейс 06:00 из
Санкт-Петербурга. Получится: Санкт-Петербург 0/2, Москва 2/2,
3 непокрытых рейса и 3 неполных пары, «Нет допустимой замены».
Порядок можно продолжить явной приёмкой CASE-01 в 10:00: местный резерв
становится 1/2; пропущенные рейсы CASE-09 остаются непокрытыми.

## Как запустить на компьютере команды

После получения изменений в репозитории, из корня Project_VSM:

```powershell
docker compose -f docker-compose.yml -f docker-compose.database.yml up -d --build
```

Сохранение существующего тома PostgreSQL обязательно: Flyway применяет только
новую V4. Старые V1–V3 не переписывались. Для этого обновления удалять том не нужно.
Открыть http://localhost:5173. Профиль API — database.

В «Источник и история решений» есть ссылка `/?operations=<session UUID>`.
URL также сохраняется в адресной строке при загрузке. Перезагрузка страницы
и перезапуск API сохраняют отказ, замену, приёмку и версию. После перезапуска
API требуется обычный повторный вход; данные берутся из БД, а не Store.

## Что сохраняет БД

- `vsm.operational_session`: источник immutable snapshot, текущая версия сессии.
- `vsm.operational_revision`: последовательные состояния, автор из сессии
  авторизации, время записи и канонический SHA-256 payload.
  UPDATE/DELETE/TRUNCATE запрещены триггерами.
- Исходный `scenario_snapshot` и `fixed_trip` сохраняются как были. Оперативные
  назначения — отдельная история решений, а не переписывание фиксированного графика.

Команды содержат `expectedVersion`, отсутствующая версия отвергается.
Сервер блокирует голову сессии в транзакции, проверяет версию и повторно
оценивает кандидата. Устаревшее решение получает 409 и не расходует резерв повторно.
API и DTO описаны в contracts/openapi.yaml, пути /operations.

## Границы, которые надо проговорить на защите

Это проверяемый модельный оперативный день парка из 43 составов, реакция на
введённый оператором отказ. Расписание, история, отказы и документы приёмки
синтетические. Подготовка 55 минут — явное допущение сценария, которое A1 должен
согласовать с заказчиком; экспертные 20–25 минут посадки не равны автоматически
полному времени подготовки.

Переход модельного времени рассчитывает пробег/положение/счётчик по покрытым
рейсам. Это моделирование исполнения, не телеметрия фактически совершённых рейсов.

Расчёт ТО всего парка на 14 суток, уборка с принятием фактов выполнения,
скользящий горизонт, общий D2 PASS E3 и полная производственная эксплуатация
ещё не реализованы в этом блоке. Следующие сутки нельзя объявлять автоматически
согласованными после замены: нужен E3-пересчёт оборотов, ТО и уборки.

Число доступных составов в момент времени не является КЭГ. Требование 88%/89%
нужно уточнить с A1: точное значение, формулу, горизонт и состав знаменателя.
На экране прямо указано, что КЭГ пока не рассчитан. Политика обязательного
статического резерва F2 не менялась: новый оперативный блок показывает разрешённый
обмен резервом отдельно. При интеграции E3 эти трактовки необходимо согласовать.

Фраза для защиты: «Мы показываем реакцию на отказ перед отправлением:
проверенную замену на оставшийся суточный оборот, цену решения в виде дефицита
резерва и восстановление резерва после явной приёмки ремонта. Полное планирование
обслуживания на 14 суток — следующий этап».

## Передача ролям

- F1: подключить компонент RecoveryConsole и новый API на главной странице;
  сохранить версионность и POST-проверки. Новая сессия восстанавливается по URL.
  В актуальном удалённом main другой App.tsx: при merge сохранить его оформление
  и переводы, добавив этот блок; не заменять файл старой версией целиком.
- F2: согласовать динамический обмен резервом с E3, пересчитывать последующие
  сутки, обязательства и уборку после изменения носителя оборота. В текущем
  блоке нет вызова CP-SAT и нет заявления о полном плане E3.
- D1: V4 и журнал оперативных решений реализованы; следующие работы — факты
  принятой уборки, реальное подтверждение допуска, длительный горизонт и импорт
  источника, если заказчик его предоставит.
- D2: тесты блока выполнены. Общий независимый аудит изменённых назначений
  вместе с полным планом E3 остаётся отдельной задачей; текущая оперативная
  допустимость не подменяет отчёт D2.
- A1/A2: подтвердить подготовку, момент уборки, правила обмена резервом,
  полномочия приёмки и формулу КЭГ; использовать именно модельную маркировку.
