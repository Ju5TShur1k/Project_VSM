# Задача 1 → совместный E3 и независимый D2

База реализации: main `a739cd3`, включая новый поиск кандидатов E3. Этот блок хранит данные, не меняет CP-SAT и frontend.
Миграция V8 добавляет 3 таблицы; V1–V7 не изменены. Старые зарегистрированные
источники и сохранённые snapshot не переписываются. Источник без новых фактов
сохраняет прежний JSON/hash. Канонизация остаётся `pg-jsonb-text-v1`, внешний
формат — `d1-source-1.0`; расширение явно помечено `e3SourceFactsVersion=e3-source-facts-1.0`.
Ключи расширения добавляются только при наличии новых фактов.

## Что брать F2 и D2

Получать **сохранённый** snapshot по snapshotId из новой версии; сверять его ID/hash.
`trainReleases` — один актуальный факт на состав в этой версии источника:

| Поле | Значение |
|---|---|
| id, scenario_id, train_id | Идентичность факта, конкретной версии и состава |
| frozen_work_id | Связь с уже закреплённой работой; может быть null для внешнего факта |
| available_from, location | Не раньше этого времени и в этом городе состав можно рассматривать для назначения |
| basis=ACCEPTED | Фактическая приёмка, confirmation_status=CONFIRMED; обязательны accepted_at и acceptance_document |
| basis=FORECAST | Прогноз, confirmation_status=UNCONFIRMED. **Не разрешает** использовать состав как выпущенный |
| basis=DEMO_ASSUMPTION | Явное допущение модельного сценария, confirmation_status=SYNTHETIC. Разрешено лишь в помеченной демонстрации |
| recorded_by, source | Автор из серверной сессии и источник основания |

Состав MAINTENANCE/FAILED без подходящего факта не становится пригодным от одного
окончания UNAVAILABLE. Факт выпуска не отменяет занятость, закреплённые работы,
обязанности по пробегу или уборке. Все эти ограничения нужно учитывать совместно.
Нельзя превращать конец рассчитанного ТО в фактическую приёмку. В плане F2 нужны
отдельные условия выпуска; фактическая эксплуатация требует подтверждения исполнения.
Этот блок **не** зачитывает циклы ТО и не добавляет service_credit при выпуске.

`urgentWorkRules` — каталог данной версии, таблицы urgent_work_rule / urgent_work_rule_resource:
id, work_kind, rule_version, duration_minutes, resource_ids, confirmation_status, source.
resource_ids — **альтернативные одиночные ресурсы**, выбрать один; это не требование
одновременно занять все пути. Каталог не поддерживает пакет многоресурсных операций.

При наличии каталога `urgentWorkRequirements` дополнительно содержит:

| Поле | Как использовать |
|---|---|
| earliest_start_at | Нижняя граница, учитывает завершение текущего рейса при not_before_current_trip_end=true |
| deadline_at / latest_end_at | Явный/вычисленный срок; latest_end_at ограничен горизонтом, работа должна **закончиться** до него |
| duration_minutes / resource_ids | Длительность и допустимые ресурсы из текущего каталога; это не выбранный слот |
| rule_id, rule_version, rule_source, rule_confirmation_status | На каком нормативе основана потребность |
| rule_status=READY | Норматив найден и CONFIRMED либо SYNTHETIC; SYNTHETIC допустим только в модельной демонстрации |
| rule_status=MISSING_RULE / UNCONFIRMED_RULE | Потребность сохранена, обоснованного расчёта нет; показывать конкретную проблему, запрещать PASS/утверждение |
| blocks_next_departure=true | IMMEDIATE/CRITICAL: нельзя назначать следующий выпуск до устранения и проверки; это не приказ прервать текущий рейс |

Если каталога нет, прежняя форма urgentWorkRequirements сохраняется без длительности.
Это **не** нулевая работа и не разрешение проигнорировать срочную заявку.
При смене каталога новая версия пересчитывает нормативные поля открытых потребностей;
старый snapshot и прежнее основание расчёта остаются неизменными.
У неизвестной работы нет выдуманной длительности; у неподтверждённой нет разрешения на PASS.
Срочная работа сама по себе не поглощает пробеговые циклы: пока A1 не подтвердит такое
правило, D2 не должен зачитывать её как плановое IS.

## API записи

`POST /api/v1/scenarios/{exactScenarioId}/source-fact-versions`, только TECHNOLOGIST,
с сессионной cookie и CSRF. Тот же конверт задачи 1:

```json
{
  "scenarioId": "UUID конкретной текущей версии",
  "expectedVersion": 0,
  "idempotencyKey": "уникальный ключ команды",
  "reason": "почему меняем данные",
  "source": "откуда факт или норматив",
  "change": {
    "kind": "TRAIN_RELEASE",
    "trainId": "UUID состава",
    "frozenWorkId": "UUID закреплённой работы",
    "availableFrom": "2031-07-02T00:00:00+03:00",
    "location": "SPB_DEPOT",
    "basis": "DEMO_ASSUMPTION"
  }
}
```

Для реального ACCEPTED обязательны acceptedAt и acceptanceDocument; acceptedAt
не может быть в будущем, после availableFrom или до окончания указанной работы.
Для FORECAST/DEMO_ASSUMPTION поля приёмки запрещены. Факт относится к тому же
составу и депо, что закреплённая работа. Неизвестные ID отклоняются.

Другой вариант change:

```json
{
  "kind": "URGENT_RULE_CHANGE",
  "version": "demo-e3-source-v1",
  "rules": [
    {
      "workKind": "Внеплановый осмотр",
      "durationMinutes": 60,
      "resourceIds": ["SPB-PATH-1", "SPB-PATH-2"],
      "confirmationStatus": "SYNTHETIC"
    }
  ]
}
```

Это полная замена каталога **в новой версии**; включать все нужные виды работ.
Длительности 60/120 минут для внеплановых работ — допущения демонстрации,
не сведения кейса и не подтверждение эксперта. Только технолог меняет каталог.
Диспетчер сообщает workType/workKind и срок, не задаёт длительность или занятый слот.

Ответ — существующий ChangeReceipt с новой версией, snapshotId/hash и историей.
Точный повтор возвращает тот же результат; устаревшая версия или изменённый повтор — 409.
Неверные данные — 422, отсутствие прав — 403; неуспешная команда не создаёт частичную версию.
Новый endpoint не запускает расчёт автоматически: сначала подключить совместный E3.
Для ручного job использовать newScenarioId из receipt и hash этой версии.

`GET /scenarios/{rootId}/version` — актуальная версия; `GET /scenarios/{exactId}/source`
— исходные факты **конкретной** версии; `GET /scenarios/{exactId}/urgent-work-rules`
— каталог для формы или проверяющего. `/change-requests/{id}` и `/history` сохраняют основание.
Старые UI-формы и их payload не изменены; вид работы должен точно совпадать с work_kind.

## Воспроизводимая модель для пяти составов

После загрузки FULL43 получить его root scenarioId. Из корня проекта в PowerShell:

```powershell
./database/demo/prepare_e3_source.ps1 -ScenarioId 'ROOT_UUID' -BaseUrl 'http://localhost:8080'
```

Скрипт входит демонстрационным технологом (пароль можно передать параметром), проверяет
MODELLED FULL43, 43 состава/1428 рейсов/5 путей. Через API добавляет 4 вида срочных
работ и 5 DEMO_ASSUMPTION выпусков. Доступность — не раньше следующих суток,
окончания имеющейся UNAVAILABLE и закреплённой работы. Приёмку не выдумывает.
Существующие выпуски и чужой каталог не перезаписывает. Повторный запуск не меняет hash.
Старый исходный набор сохраняется; на выходе — точная новая версия/snapshot/hash.
Скрипт **не** добавляет отказ/срочную заявку и не рассчитывает/не утверждает план.

Сначала использовать выделенный модельный источник и согласовать допущения с A1.
Не выдавать эти выпуск/длительности за факты оператора. Уточнить у A1: приёмочные
операции, их длительность/ресурс, разрешение движения, подтверждение выполнения и
зачёт циклов. Эти детали остаются зависимостями полного E3.

## Граница интеграции

Legacy SourceSnapshotE2Adapter и SourceSnapshotE3Adapter явно отклоняют непустые
trainReleases/urgentWorkRules. Это защищает от расчёта по неполным ограничениям.
Старый D2 E3 также отвергает неизвестное расширение; его whitelist нельзя просто
расширить без проверки новых правил. Обычные источники без расширения продолжают работать.

F2: читать новый контракт в совместном адаптере, выбирать назначения и интервалы,
сохранять solverStatus и план по этому hash. D2: из того же сохранённого snapshot
самостоятельно проверять выпуск, норматив, срок и выбранный ресурс; находить план
с преждевременным выпуском/неизвестным нормативом. Frontend: после изменения получать
head, открывать новый planId; отдельно показывать solverStatus и d2Status.
Один этот контракт не делает FULL43 утверждаемым и не доказывает допустимость расписания.
