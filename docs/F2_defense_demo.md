# F2: основной демонстрационный путь к защите

## Запуск и проверка

Нужен Docker Desktop и свободные порты 8080 и 5173. Из корня репозитория:

```powershell
docker compose up -d --build
docker compose ps
```

Открыть `http://localhost:5173`, войти `planner` / `planner-demo` (если пароль не переопределён).

1. Нажать «Загрузить демонстрационные исходные данные». API создаёт синтетические факты E2 в PostgreSQL и фиксирует неизменяемый snapshot D1. На главной видны `scenarioId` и полный SHA-256 hash.
2. Нажать «Рассчитать план». Следить отдельно за жизненным циклом задания, результатом solver и статусом D2. Календарь загружается из `GET /api/v1/plans/{planId}/calendar` после расчёта.
3. Выбрать прибытие R1 `00:55`, нажать «Сохранить новый snapshot». Hash должен измениться. Старый snapshot сохранится в БД.
4. Ещё раз рассчитать. В календаре рейс R1 теперь заканчивается в `00:55`, сервис IS200 начинается в `00:55`. Hash результата должен совпасть с новым hash на главной. Сравнивать интервалы и hash, не только статус solver.

На одном сценарии повторное сохранение того же времени возвращает тот же snapshot ID/hash. Диапазон изменения `00:50`–`01:00` выбран так, чтобы синтетическое 30-минутное обслуживание помещалось до фиксированного рейса R2 в `01:30`.

## Откуда берётся результат

- `DemoSourceService` пишет только явно помеченные демонстрационные факты: 1 состав, 3 фиксированных рейса, 1 путь, историю зачёта IS100, правила IS100/IS200, проверенное синтетическое окно присутствия и доступности.
- `SourceSnapshotRepository.capture` сохраняет канонический payload и hash. По ID этого снимка `SourceSnapshotE2Adapter` готовит F2 `ScenarioSnapshot`; job не перечитывает живые таблицы во время расчёта.
- `CpSatPlanner` расставляет обязательную работу, не перемещая заданные рейсы. `PlanCalendarProjector` соединяет исходные рейсы и фактические интервалы результата в ответ API с источником и объяснением.
- `IndependentIntervalAudit` проверяет структуру и пересечения как частичная диагностика. Полная независимая D2-проверка пробега, уборки и допуска ещё не подключена. `validationStatus=NOT_PERFORMED`; UI и сервер запрещают утверждение.
- Отдельная ручная заготовка календаря доступна только по `/?calendarDemo=1` и прямо обозначена как ручной пример. На главной ссылки на неё нет.

## Границы этого блока и передача коллегам

- **F1:** задания и планы пока в памяти. После перезапуска API их нужно пересоздать; для защиты с восстановлением истории требуется хранение jobs/plans и привязки к snapshot в PostgreSQL. Сохранённые D1 snapshot уже переживают перезапуск.
- **D1:** интеграция использует узкий E2-адаптер. Для полного E3-пути нужен адаптер, который сохраняет и передаёт occupancy, cleaning, frozen work и остальные подтверждённые факты без отбрасывания.
- **D2:** реализовать полную независимую проверку результата по исходному payload, включая пробег, циклы, окна, уборку, резерв и выпуск; подключить `PlanValidator` только после этого. Статус `PASS` должен относиться к тому же hash и результату.
- **F2:** после E3-адаптера расширить основной расчёт с одного E2-состава на парк и его подтверждённые ограничения. Пределы и нормативы до подтверждения A1 остаются явно синтетическими.

`docker compose` запускает профиль БД. При запуске backend без `database` главная загрузка возвращает ошибку с объяснением, что нужен профиль БД. Для интеграционных тестов D1/F2 использовать отдельную пустую PostgreSQL базу через `D1_TEST_DB_URL`; тест `SourceSnapshotE2AdapterTest.changingSourceTripCreatesNewHashAndMovesCalculatedCalendar` проверяет критерий на DB и настоящем solver.
