# D2: независимая проверка плана и доказательства для защиты

Подключена проверка E2 по сохранённому источнику PostgreSQL. Для E3 добавлены независимые проверки назначения рейсов и пересчитанных пробеговых рубежей, сверка проекции с исходным snapshot, диагностика отсутствующих окон, дефицита резерва по городам и уборок после переназначения. Это отдельные проверяемые части: общий E3 D2 не выдаёт PASS, пока solver не разместит ТО и недостающие уборки, а аудит не проверит ресурсы, выпуск и полный оборот. Текущий статус полного парка описан в [E3_HANDOFF.md](E3_HANDOFF.md).

## Что теперь происходит

1. D1 фиксирует исходные факты и версию правил в неизменяемом snapshot с SHA-256.
2. F2 строит проекцию и размещает целые сервисные циклы.
3. `DatabasePlanValidator` на профиле `database` отдельно читает сохранённый payload. Для E2 `SourcePlanAudit` заново восстанавливает пробеговые обязанности, не вызывая генератор F2, его поиск окон или решатель. Для E3 `E3SourcePlanAudit` пока проверяет соответствие исходных фактов и проекции, но не восстанавливает все пробеговые обязанности.
4. D2 проверяет итоговые интервалы. Неподдерживаемая версия, неизвестное поле источника или потерянное обязательство блокируют PASS.
5. API связывает отчёт с исходным snapshot, содержимым событий и версией плана. Утверждение изменённых событий со старым PASS возвращает 422.

Особенно важна проверка ошибки общего происхождения: если генератор F2 забыл работу и солвер успешно решил уже неполную задачу, D2 всё равно восстанавливает эту работу из источника и отклоняет план. Такой случай проверен интеграционным тестом с настоящим CP-SAT.

## Выполнение плана D2

| Задача | Реализовано | Что ещё требуется |
|---|---|---|
| D2-1: независимые проверки | E2: полнота циклов, зачёты, поглощение на совпавшем рубеже, длительности, границы пробега, фиксированные рейсы, непрерывность маршрута, присутствие, ресурсы, пересечения | Связать проверки E3 с полным исходным контрактом; расчёт FULL43 пока запрещён |
| D2-2: отчёт и запрет утверждения | Отдельный `ValidationReport`, source/hash/version, hash событий, машиночитаемые причины с объектом и интервалом; сервер проверяет привязку перед утверждением | F1: долговременное хранение job/plan/report в БД; сейчас они в памяти процесса |
| D2-3: отрицательные примеры | Пропущенная/укороченная работа, ошибочный источник, общий пропуск F2, изменённые события, рейсовый конфликт; отдельно проверены уборка, frozen, подготовка, выпуск, резерв, станок | API-тесты всех E3-примеров после подключения исходного контракта E3 |
| D2-4: честные показатели | Обязанности/размещённые работы, составо-часы ТО, исходные и конфликтующие рейсы, нагрузка ресурса, следующие рубежи | A1: формула готовности и правила для расчёта KPI всего парка |
| D2-5: базовое сравнение | EDD и CP-SAT на одинаковом snapshot E2_6 и BLOCKED6; seed, лимит, версии, статусы и результаты сохранены | Более сложные согласованные сценарии; текущий пример не доказал улучшения качества CP-SAT |

## Область PASS

`E2_MODEL` означает, что модельный план соответствует своему модельному источнику. Численные нормы IS100/IS200 взяты из кейса; расписание, начальные одометры и политика зачёта моделируются. Это не разрешение фактического выпуска поезда. Утверждается версия плана обслуживания, статус поезда в БД при этом не меняется.

`E2_SOURCE` предусмотрен для подтверждённой версии правил в той же узкой области E2. Даже этот статус не проверяет уборку, резерв, приёмку или календарные обязанности. Они перечислены в сообщении `D2_SCOPE_E2`.

`FULL43` содержит факты E3 и не пропускается через E2-проверку. Старый импорт без исходного D1 snapshot также не получает PASS. Backend без профиля `database` сохраняет блокирующую заглушку NOT_PERFORMED.

## Контракт отчёта

В `Plan` добавлены `validationReport` и `metrics`; в `Validation` — необязательные `objectId`, `startAt`, `endAt`. Изменения отражены в `contracts/openapi.yaml`, API v1 сохранён. Внутренняя версия отчёта: `d2-validation-1.0`.

Отчёт содержит `scenarioId`, `sourceSnapshotId`, `snapshotHash`, `resultHash`, `policy`, `solverStatus`, `planVersion`, `checkedAt`, версию/подтверждение правил, независимо полученное число обязательств и следующие рубежи за горизонтом.

Fingerprint `d2-plan-events-v1` — SHA-256 от полей с префиксом длины: версия канонизации, scenario/hash, число событий, отсортированные ID, trainId, kind, начало/конец как Instant, отсортированные resourceIds с числом ресурсов. Перестановка событий и эквивалентные UTC offsets не меняют hash; перенос, удаление или изменение назначения меняют. Источник проверяется отдельно по точным сохранённым UTF-8 байтам `pg-jsonb-text-v1`.

До утверждения отчёт связан с версией 0. Утверждение создаёт версию 1 и сохраняет отчёт о проверенной исходной версии; повторная отправка версии 0 получает 409, попытка повторно утвердить новую версию старым отчётом — 422. Новый расчёт создаёт новый план и проверку.

| Статус | Значение |
|---|---|
| PASS | Проверка полностью прошла в явно указанной области |
| FAILED | Есть CRITICAL: нарушение, отсутствующее правило или неподдерживаемый источник |
| NOT_PERFORMED | Валидатор не подключён в выбранном профиле |

`SUCCEEDED` — завершение задания, `OPTIMAL/FEASIBLE/...` — вывод алгоритма, PASS — независимая проверка. Это три разные характеристики. UNKNOWN не доказывает невозможность. INFEASIBLE у CP-SAT относится к конкретной модели ограничений.

Основные коды: `D2_REQUIRED_WORK_MISSING`, `D2_PROJECTION_MISSING_WORK`, `D2_WORK_DURATION`, `D2_MILEAGE_TOO_EARLY`, `D2_MILEAGE_DEADLINE`, `D2_LOCATION`, `D2_SOURCE_PRESENCE`, `D2_SOURCE_RESOURCE_WINDOW`, `D2_FIXED_TRIP_CHANGED`, `D2_SOURCE_TRIP_OVERLAP`, `D2_SOURCE_HASH`, `D2_E3_SOURCE_UNSUPPORTED`. У ошибок размещения указан ID работы и её интервал; у ошибок источника интервал может отсутствовать.

## Подготовленные проверки E3

`OperationalEvidenceAudit` не вызывает F2 и не подставляет неизвестные правила. Его функции возвращают замечания; сами по себе они не выдают разрешение или общий PASS.

| Функция | Явный вход от D1/A1 | Проверяемое нарушение |
|---|---|---|
| `cleaning` | Тип CLEANING, начальные счётчики, число рейсов до уборки и диапазон длительности | После четвёртого прибытия нет полной уборки до следующего отправления; нет счётчика/правила; обязательство на конце горизонта сохраняется |
| `reserve` | Пригодность каждого состава к резерву по городу и времени; требование количества по каждому городу и периоду | В одном городе недостаточно свободных пригодных составов, хотя суммарно четыре; занятые рейсом/работой составы не считаются |
| `frozen` | Закреплённые интервалы с составом и ресурсом | Работа исчезла или поменяла время/назначение |
| `release` | Тип RELEASE_CHECK и связь с обслуживанием | Контроль отсутствует, начался до окончания ТО или закончился после следующего отправления |
| `preparation` | Явное время подготовки для каждого рейса | ТО или предыдущий рейс попадает в подготовительный интервал |
| `locations` | Город выполнения для работы и город ресурса | Например, обточка назначена на ресурс MSK при разрешённом SPB |
| `calendar` | ID календарной работы, срок и источник правила | Обязанность в горизонте пропущена/просрочена; будущий срок отмечен как pending |
| `pairs` | Явный ключ пары для каждого рейса | В нитке отсутствует второй состав либо времена/расстояние не совпадают |
| `maintenanceCapacity` | Типы обслуживания, предел и источник | На разных путях одновременно обслуживается больше разрешённого числа составов |

Приёмка в расписании — планируемая операция. Для фактического выпуска требуется отдельное принятое событие с результатом, ответственным и временем. На основе одного запланированного RELEASE_CHECK нельзя обновлять фактический статус поезда.

Резерв считается по явно заданной пригодности и требованиям. Если допускается временно использовать резерв, A1 должен предоставить отдельные периоды сниженного требования и правила восстановления; валидатор не придумывает их. Пригодность должна включать город и подтверждённую готовность, а не только отсутствие работ.

## Передать коллегам

**D1:** расширить версионированный source payload: ключи пар, окна пригодности резерва по городам, требования резерва по периодам, уборочные правила/счётчики, подготовительные интервалы, календарные обязанности, зависимости выпуска и классификацию занятости как ТО/уборка/сбой. Для каждого значения нужен источник и подтверждение. Менять snapshot только созданием новой версии.

**A1:** подтвердить правила поглощения/допусков, город и ресурсы операций, подготовку, фактическую приёмку, использование резерва, календарные сроки; разрешить противоречия по обточке и формуле 88%/89%. Числа не вводить молча в код.

**F2:** подготовить полную E3-проекцию и итоговые типизированные блоки с ID исходных обязанностей; передать парность, release-связи и закреплённые интервалы. Отдельный рейс не должен пропадать при подготовке проекции.

**F1:** вызвать полную комбинацию исходных D2-проверок после расширения контракта, сохранить отчёт/план/job в PostgreSQL одной согласованной операцией и запретить утверждение при неизвестной области. Текущий профиль database уже вызывает E2-validator; менять HTTP-поток повторно не нужно.

**Участник, который делает презентацию:** пользоваться измерениями из `D2_COMPARISON.md`, показывать модельную происхождение данных, 12/12 обязательств и отрицательный сценарий. Не заявлять готовность 89%, экономию или полноту E3. Для слайда о проверке: «План независимо сверяется с исходными рейсами, пробегом и нормами; пропущенную работу выявляем даже при успешном расчёте».

## Показатели

- `requiredServiceCount` — независимое число обязательств, `placedServiceCount` — число итоговых работ, `missingServiceCount` — разность. Для непроверенного/ошибочного плана `metrics=null`, а причины и ожидаемое число остаются в отчёте.
- `trainServiceMinutes` — сумма длительностей по составам; параллельные работы суммируются. Деление на 60 даёт составо-часы.
- `scheduledTripCount` — фиксированные рейсы в проверенном источнике. Это не фактически выполненные перевозки. `conflictingTripCount` — число таких рейсов с пересечением ТО того же состава.
- Нагрузка ресурса — минуты запланированных работ / минуты всего горизонта × 100. Это не процент загрузки доступных смен и не готовность парка.
- `makespanMinutes` — конец последней работы от начала горизонта; ожидание между работами входит в показатель.
- Следующий рубеж рассчитывается отдельно для каждого состава и цикла после конечного модельного пробега. Это остаток до номинального рубежа, не до границы допуска; позднее старший цикл может поглотить младший.

## Повторить проверку

Java 21. Интеграционные тесты запускать только на отдельной тестовой БД; не на рабочей БД команды. Без `D1_TEST_DB_URL` DB-тесты пропускаются — такой запуск не подтверждает интеграцию.

```powershell
cd backend
$env:D1_TEST_DB_URL='jdbc:postgresql://127.0.0.1:55440/case_fleet_28'
$env:D1_TEST_DB_USER='d1test'
$env:D1_TEST_DB_PASSWORD=''
$env:D2_BUILD_COMMIT=(git rev-parse HEAD)
./mvnw.cmd verify
cd ../frontend
npm.cmd run build
```

Адрес/учётные данные в примере относятся только к локальному тестовому кластеру автора; на другом ПК указать свою отдельную тестовую БД. `D2DatabaseIntegrationTest` создаёт `backend/target/d2-comparison.json`; его версия для защиты сохранена в `database/reports/`.

Отрицательные unit-тесты не заменяют интеграцию E3. Для E2 есть HTTP-тесты запрета изменённых событий, неверного hash/версии, отсутствующих обязанностей и недопустимого результата. В рабочую систему команды эти изменения ещё нужно закоммитить, объединить и пересобрать контейнеры.
