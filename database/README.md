# D1: первый блок БД

Статус: основа хранения исходных данных и immutable snapshot. Это не подключение mock API к планировщику и не разрешение утверждать план.

## Что сделано

- Профиль Spring `database`, PostgreSQL JDBC, Flyway, миграции V1–V3.
- 17 таблиц в схеме `vsm`: исходные факты E2 и дополнительные факты E3.
- Java `SourceSnapshotRepository`: сохранить согласованный снимок исходных данных и прочитать его по ID.
- Неизменяемые снимки, канонический текст и SHA-256; повторное сохранение одинакового содержимого возвращает существующий снимок.
- Синтетические примеры, SQL-проверки ограничений, интеграционные тесты профиля.
- Docker Compose override: PostgreSQL 16 на localhost:5433, чтобы не конфликтовать с установленной локальной БД на 5432.

## Запуск на Windows

Из корня репозитория:

```powershell
docker compose -f docker-compose.yml -f docker-compose.database.yml up -d --build
docker compose -f docker-compose.yml -f docker-compose.database.yml ps
docker compose -f docker-compose.yml -f docker-compose.database.yml logs api
```

При первом запуске Flyway применяет V1–V3. В pgAdmin: host `localhost`, port `5433`, database/user/password `okno` (локальная демонстрация).
Требуется современный Docker Compose с поддержкой `!override` (на этом компьютере установлен v5.5.1).
Существующий volume PostgreSQL не удалять. Если он ранее создавался с другими реквизитами, переменные Compose не поменяют пароль существующей БД автоматически.

Для запуска backend из IDE: JDK 21, профиль `database`, `DB_URL=jdbc:postgresql://localhost:5433/okno`, `DB_USER=okno`, `DB_PASSWORD=okno`.
Без профиля сохраняется прежний mock-режим F1 без подключения к PostgreSQL. Даже с профилем текущие HTTP-методы пока используют `Store`: миграция API на репозитории — отдельный следующий блок F1/D1.

## Какие данные где лежат

| Таблицы | Смысл |
|---|---|
| `scenario` | Горизонт расчёта, версия правил, источник сценария |
| `train`, `odometer_reading` | Поезда и фактические замеры пробега с датой |
| `rule_set`, `cycle_rule` | Версии регламентов, интервалы, длительности, допуски, статус подтверждения |
| `resource`, `resource_availability`, `cycle_resource` | Ресурсы, явные окна доступности, допустимые ресурсы для цикла |
| `fixed_trip` | Фиксированные рейсы с временем и расстоянием |
| `service_event`, `service_credit`, `cycle_baseline` | Принятое ТО, зачтённые циклы, явно заданная исходная история |
| `train_presence` | Подтверждённые/неподтверждённые/синтетические окна нахождения поезда в месте |
| `train_occupancy` | Дополнительная занятость: статический резерв, уборка, недоступность |
| `cleaning_counter` | Счётчик завершённых рейсов после уборки на определённый момент |
| `frozen_work` | Закреплённая работа с фиксированным поездом, ресурсом и временем |
| `scenario_snapshot` | Неизменяемая копия всех перечисленных исходных фактов для сценария |

Все времена — `timestamptz`, границы интервалов `[начало, конец)`. Храним момент времени; исходное текстовое смещение не сохраняется PostgreSQL. При сохранении snapshot времена сериализуются в UTC.
Пробег и расстояния — целые километры, как в текущем F2. Нельзя молча округлять дробные значения при импорте.
Наличие строки в таблице или сохранённого snapshot не означает, что данные полны, подтверждены либо пригодны для выпуска поезда.

Важный пример: IS200 может быть выполнен при 24 000 км, а зачесть рубеж 25 000 км. `actual_odometer_km` и `credited_nominal_km` — разные поля. Зачёт младших циклов записывается явно, а не вычисляется по рангу без подтверждения A1.
Нулевая история тоже должна быть явным фактом в `cycle_baseline` с источником. Отсутствующая запись означает неизвестность, а не 0.
`service_event` содержит завершённые принятые работы; время завершения и время приёмки разделены. Историческое ТО может ссылаться на прежнюю версию правил.

Версии правил нельзя менять/удалять. После ссылки из сценария или истории нельзя дописывать циклы в используемую версию. Сначала загрузить полный набор правил, затем создать сценарий. Исправления — новая версия.
Нулевой счётчик уборки нельзя подставлять при отсутствии замера. `last_cleaning_accepted_at` допускает NULL, если известен счётчик, но не время последней уборки; источник обязателен.

## Snapshot и hash: контракт для F1/F2/D2

Предлагаемый внутренний формат D1: `d1-source-1.0`; не путать с `ScenarioSnapshot 1.1` F2. Поля и способ канонизации нужно согласовать до интеграции общего DTO.

```sql
SELECT id, scenario_id, snapshot_hash, canonicalization
FROM vsm.capture_snapshot(
    '20000000-0000-0000-0000-000000000001',
    gen_random_uuid()
);
```

Java: `SourceSnapshotRepository.capture(scenarioId)`; `findById(snapshotId)` возвращает `Optional<SourceSnapshot>`.

1. Все исходные таблицы читаются одной STABLE SQL-функцией в одном согласованном MVCC-снимке. Функция не собирает половину данных до изменения рейсов и половину после.
2. Массивы упорядочены по явным стабильным ключам. Текстовые ключи используют collation `C`; время — UTC и ISO.
3. Канонизация `pg-jsonb-text-v1`: точный PostgreSQL `jsonb::text`, UTF-8, без BOM и завершающего перевода строки. Это **не RFC 8785/JCS** и не произвольная сериализация Jackson.
4. Hash — lowercase hex SHA-256 от `canonical_payload`. Сам hash, ID снимка и время захвата не входят в payload. Метаданные исходных записей входят.
5. F1/F2 передают сохранённый hash, D2 может независимо проверить SHA-256 от точных UTF-8 байтов `canonical_payload`. После разбора и повторной сериализации JSON байты могут отличаться — так проверять нельзя.
6. Одинаковый набор фактов возвращает прежний snapshot/ID. Изменение рейса, правил, уборки или закреплённой работы создаёт новый hash. Старый снимок не меняется.
7. UPDATE/DELETE/TRUNCATE снимков блокируются триггерами; старый snapshot хранит копии фактов, а не только ссылки на изменяемые таблицы.
8. Неизвестный scenarioId — ошибка. Пустой набор работ или рейсов допустим как исходные данные; пригодность к расчёту проверяется отдельно. При конфликте транзакций уровня SERIALIZABLE/REPEATABLE READ вызывающая сторона повторяет всю транзакцию.

Выпуск V1–V3 образует первый внутренний формат. После публикации миграции не редактировать: изменения схемы — V4 и далее, изменение формата payload — новая версия контракта/канонизации.
Канонизация привязана к PostgreSQL; при смене major-версии проверять эталонные значения либо выпускать новую версию. Целевая версия проекта — 16.

## Данные E3 и границы ответственности

`trainPresence`, `trainOccupancy`, `cleaningCounters`, `frozenWork` включены в полный hash. Пустой список присутствия/доступности не даёт права считать поезд или ресурс доступным всегда.
Для реальных расчётов используются подтверждённые сведения; `SYNTHETIC` допускается только в явно помеченной демонстрации. Нельзя выдавать `UNCONFIRMED` за подтверждённые данные или молча выбрасывать их из расчёта.
Закреплённые работы — входные ограничения, а не новый свободно перемещаемый результат. F1 обязан связать их с конкретным снимком job; смена входных работ меняет hash.

Динамический резерв, решение о допуске к выпуску и скользящий горизонт здесь **не реализованы**. Строка `RESERVE` фиксирует уже заданную занятость, а не выбирает составы в резерв. Поле приёмки исторического ТО не заменяет будущую процедуру приёмки перед выпуском.
Пересечения рейсов одного поезда и закреплённых работ одного поезда/ресурса запрещены внутри соответствующих таблиц. Межтабличные конфликты (рейс против закреплённой работы, отсутствие присутствия, недоступный ресурс) должны проверять адаптер и D2; сама БД ещё не доказывает допустимость плана.

## Синтетические примеры

Файлы в `database/demo` загружать только в демонстрационную базу после миграций, однократно. Повторный запуск завершится ошибкой уникальности и откатится при `--single-transaction`.

```powershell
$env:PGPASSWORD = 'okno'
$psql = 'C:\Program Files\PostgreSQL\18\bin\psql.exe'
& $psql -h localhost -p 5433 -U okno -d okno -v ON_ERROR_STOP=1 --single-transaction -f database/demo/seed_synthetic.sql
# Дополнительные факты E3, если нужны:
& $psql -h localhost -p 5433 -U okno -d okno -v ON_ERROR_STOP=1 --single-transaction -f database/demo/seed_operational.sql
```

`psql` 18 здесь клиент; сервер в Compose остаётся 16. Демодлительности 20/30 минут искусственные, их нельзя показывать как реальные нормативы IS100/IS200.

## Проверки

Обычные проверки backend:

```powershell
cd backend
.\mvnw.cmd verify
```

Интеграционные проверки БД: выделить отдельную пустую UTF-8 базу (например `okno_d1_test`), затем:

```powershell
$env:D1_TEST_DB_URL = 'jdbc:postgresql://localhost:5433/okno_d1_test'
$env:D1_TEST_DB_USER = 'okno'
$env:D1_TEST_DB_PASSWORD = 'okno'
.\mvnw.cmd verify
```

Flyway создаст таблицы в этой базе. Из корня репозитория выполнить SQL-проверки на той же тестовой базе:

```powershell
& 'C:\Program Files\PostgreSQL\18\bin\psql.exe' -h localhost -p 5433 -U okno -d okno_d1_test -f database/tests/constraints.sql
```

SQL-скрипт работает внутри транзакции и откатывает тестовые данные; требует пустых предметных таблиц. Проверяет отрицательные значения, ссылки, пересечения, касание границ, защиту snapshot, ранний зачёт ТО, стабильность hash при перестановке строк/смене часового пояса, изменение hash при изменении рейса/счётчика уборки.
Java проверяет реальный запуск Flyway и репозитория, идемпотентность capture, сохранность старого снимка и независимый SHA-256 через JDK, включая кириллицу.

## Что передать команде

- **F1:** профиль `database` и `SourceSnapshotRepository` готовы как точка подключения. HTTP Store пока в памяти. Для job сохранять snapshot ID/hash; запускать solver асинхронно; утверждение разрешать только после независимой проверки D2 этого же результата и snapshot.
- **F2:** таблицы истории зачёта, фиксированных рейсов, ресурсов, окон присутствия/занятости, счётчика уборки и frozen work подготовлены. Нужен адаптер из сохранённого payload в актуальный `Input` E2/E3, не из «живых» таблиц во время расчёта. При неподдерживаемых ограничениях — явная ошибка, а не их игнорирование.
- **D2:** получать исходный payload, canonical_payload/hash и итоговые интервалы; проверять независимо от внутренних методов solver. В том числе наличие обязательных данных, границы пробега, нахождение/занятость, ресурсы, уборку и неизменность frozen work.
- **A1:** подтвердить основу допуска (интервал или номинальный рубеж), абсолютную/относительную сетку ТО, поглощение циклов, длительности/ресурсы, счёт рейсов после уборки, требования резерва и приёмки перед выпуском.

Ближайший следующий блок D1: согласовать DTO с актуальным E3, реализовать импорт с диагностикой и адаптер payload → вход планировщика. Схема сама по себе не завершает эту интеграцию.
