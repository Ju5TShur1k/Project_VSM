# D1 → F2/D2: проверяемая передача данных из PostgreSQL

Статус на 27.09.2026: реализован **узкий сквозной пример E2**. Данные считываются из сохранённого неизменяемого D1 snapshot, преобразуются в задачу F2 и решаются CP-SAT. Это проверка контракта интеграции, **не готовая схема расчёта всего парка и не эксплуатационный план**. Текущий HTTP-поток F1 по-прежнему строит `SyntheticSnapshot`; экран не получает данные этого адаптера.

## Что делает адаптер

`SourceSnapshotE2Adapter.project(SourceSnapshotRepository.SourceSnapshot)`:

1. Проверяет версию D1, способ канонизации, SHA-256 точного сохранённого payload и ID сценария. Источником служит только сохранённый snapshot, а не изменяемые «живые» таблицы.
2. Читает активную версию правил, одометр на начало горизонта, явно записанную историю зачётов и фиксированные рейсы. Неподтверждённые правила и статус поезда, отличный от `AVAILABLE`, отклоняются. Поддерживаются только правила `ABSOLUTE_GRID` и `NOMINAL_MILESTONE`, целые километры/минуты и ровно один ресурс на цикл.
3. Передаёт эти факты в существующий `MileageObligationGenerator`. Генератор определяет обязательные циклы и их окна по пробегу; поглощение младших циклов остаётся в его модели. Длительности и допуски берутся из записанной версии правил. Значения тестового набора искусственные и не считаются нормативами заказчика.
4. Пересекает записанные окна присутствия поезда с календарём ресурса в одном месте. Окна с `UNCONFIRMED` отклоняются. Полученные интервалы передаются как `ServiceWindow`. Работа должна целиком попасть в такое окно.
5. Если в snapshot есть `trainOccupancy`, `cleaningCounters` или `frozenWork`, адаптер возвращает явную ошибку. Он не подставляет пустые списки и не создаёт видимость, что учёл эти ограничения.

Демонстрационный набор: после `database/demo/seed_synthetic.sql` загрузить `database/demo/seed_e2_adapter.sql` в **отдельную тестовую БД**. Сценарий `20000000-0000-0000-0000-000000000002` содержит один состав, три рейса, историю циклов и окно доступности. Он даёт обязательную работу IS200 на 30 минут в окне 00:50–01:30. Это только технический fixture.

## Что проверяет D2 сейчас

`IndependentIntervalAudit.check(source, result)` не вызывает решатель. Он независимо сопоставляет итоговые интервалы с переданным snapshot: совпадение ID/hash, полный состав работ, поезд/ресурс, длительность и окно, порядок, пересечения `[start,end)` с рейсами и занятиями, календарное окно обслуживания, закреплённые работы и число доступных резервных поездов в каждом интервале.

Аудит **не выводит заново** обязанности по пробегу из исходного D1 payload, не проверяет уборку по счётчику/рейсам, правила выпуска, реальную пригодность и распределение резерва по городам. Поэтому класс не зарегистрирован как Spring `PlanValidator`: штатный `VALIDATION_NOT_PERFORMED` остаётся блокирующим для утверждения. Отсутствие замечаний этого частичного аудита нельзя трактовать как разрешение выпуска.

## Следующий контракт для команды

- **D1:** согласовать с A1 источник и статус каждого входного факта. Добавить в модель недостающие данные E3: парность составов, принадлежность резерва городу и периоды фактической пригодности, условия уборки, подтверждение приёмки и выпуска, плюс маппинг `trainOccupancy`, `cleaningCounters`, `frozenWork` без потерь. Для каждого сценария отмечать полноту и происхождение данных.
- **D2:** из *того же* сохранённого D1 payload независимо восстановить пробег/рубежи, циклы и поглощение, проверить счётчик уборки, обязательную приёмку перед рейсом, местоположение и резерв по согласованному правилу. Добавлять Spring `PlanValidator` только тогда, когда эти проверки покрывают весь используемый режим планирования. Любая отсутствующая критичная информация должна блокировать утверждение.
- **F1:** после согласования DTO сохранять snapshot ID/hash в job, строить вход планировщика из D1 projection, показывать версию правил/происхождение и диагностировать неподдерживаемый snapshot как ошибку ввода. Переключение HTTP с `SyntheticSnapshot` на адаптер делать для согласованного E3 режима, а не подменять им действующий 43-составный демопоток.
- **F2:** согласовать вход E3 (резерв по городам, 5 одновременных ТО, парность, уборка, выпуск, скользящий горизонт) с A1. Не объявлять локальный E2 пример полноценной проверкой этих ограничений.
- **A1:** подтвердить конкретные правила зачёта IS100/IS200, допуски и длительности, маршруты/депо и перенос составов, четыре резерва по городам, пять одновременных ТО, критерии уборки и выпуска. До подтверждения держать искусственные значения помеченными как synthetic.

## Проверка

Из `backend` выполнить `mvn verify` на JDK 21. Для интеграционного теста D1 нужен **выделенный пустой** PostgreSQL: задать `D1_TEST_DB_URL`, `D1_TEST_DB_USER`, `D1_TEST_DB_PASSWORD`, затем выполнить `mvn -Dtest=DatabaseProfileTest,SourceSnapshotE2AdapterTest,IndependentIntervalAuditTest test`. Тест загружает фикстуры транзакционно, проверяет hash/проекцию/реальный CP-SAT/частичный D2 аудит и отказ от E3 фактов. Отдельная БД защищает рабочие данные; демо seed в рабочую БД не загружать.
